## 1. 문제 정의 및 기획 (심사: 문제 정의·기획성)

### 수강신청 전날 밤

전문대 학생은 2~3년 안에 졸업요건·자격증·현장실습·취업을 **동시에** 끝내야 한다. 4년제와 달리 복구할 학기가 없다 — 1학년에 선수과목이나 자격증 타이밍을 한 번 놓치면 만회가 어렵다. 그런데 학생 손에 쥐어지는 정보는 **교육과정표 PDF 한 장**이다. "시스템 엔지니어가 되려면 어느 학기에 뭘 듣고 CCNA를 언제 따야 하는가"는 아무도 알려주지 않는다. 이 정보격차는 신입생·편입생·직무를 아직 못 정한 학생에게 가장 크다.

### 기존 시스템과의 관계 — 대체가 아니라 상류 공정

학교 SMART CARE에도 "로드맵" 메뉴가 있다. 그러나 그것은 **학생이 직접 채워 등록하는 이력 관리 양식**이고, 문제는 학생이 그 빈칸에 뭘 넣을지 모른다는 것이다. 우리는 그 빈칸을 채워주는 엔진을 만들었다 — **우리 출력물이 SMART CARE의 입력물이 된다.** 학교 포털의 졸업사정 시뮬레이션이 "졸업 가능 여부의 **확인**"이라면, 우리는 목표 직무에서 역산한 "경로의 **설계**"다.

### 기획 원칙

- **데모 시나리오 한 문장으로 범위를 통제했다** — "심사위원이 학과와 직무를 고르면 학기별 로드맵과 졸업요건 충족 배지가 뜬다." 이 문장에 없는 기능은 만들지 않았고, 판단이 애매하면 이 문장으로 돌아왔다.
- **컷 라인을 사전 합의했다** — 시각별로 무엇을 포기할지 시작할 때 정했고(설계서 §8), 코어 데모가 부가 기능 때문에 깨지는 일을 금지했다.
- 20시간 안에 넣지 않기로 **판단한** 것들(채용공고 크롤링, NCS 원문 대조, 의미 매칭)을 "다음 단계"로 문서화했다 — 안 한 것과 못 한 것을 구분했다.

## 2. 기술 구현 (심사: 기술 구현 완성도)

### 아키텍처

```
                [브라우저 — React SPA]
                     │ fetch (단일 창구, 과목은 course_id로만)
                     ▼
┌──────────────── FastAPI ────────────────────┐
│ GET /depts·/report ──▶ data/*.json (읽기 전용) │
│ POST /roadmap ──▶ 추천 엔진(결정론 규칙)         │
│                    ⇄ 졸업요건 검증기 루프        │
│                    └ LLM 비교 모드(옵트인)      │
│ /auth·/me ──▶ PostgreSQL (유저 데이터 전용)     │
└─────────────────────────────────────────────┘
                     ▲
    [파이프라인] mjc.ac.kr 수집 → 추출 → 검증 → JSON
```

### 데이터 — 전 학과를 파이프라인 하나로

| 항목 | 결과 |
|---|---|
| 학과 | **34 / 35** (자유전공학과만 제외 — 과목 2개뿐) |
| 과목 | **842개** — 학년·학기·학점·이수구분·직무 라벨·NCS·현장중심 |
| 처리 경로 | **코드 파싱 100% · LLM 폴백 0회** (헤더 전수 확인 후 코드로 전환) |
| 과목 식별자 | 결정론 조립(NFKC·로마숫자 값 변환·괄호 보존) — 776과목 **충돌 0건** |

### 핵심 구조 — 생성은 엔진이, 판정은 검증기가

- **추천 엔진(메인)**: 실데이터 기반 결정론 규칙. 학교가 교육과정표에 부여한 과목↔직무 라벨로 역산한다. "왜 이 과목이냐"에 데이터로 답할 수 있고, 응답 0.1초, 언제나 같은 결과가 재현된다. **직무 미정 모드**(라벨 학점 1위 직무 추천)도 지원한다.
- **졸업요건 검증기**: 순수 규칙 코드(LLM 없음). 미달 항목마다 `{rule, label, required, actual, shortfall, fix}`를 내고, `fix` 문구가 그대로 재생성 입력이 된다(최대 3회).
- **LLM 에이전트(비교 검증)**: 같은 계약으로 Claude(`claude-sonnet-5`) 에이전트도 만들어 비교했다. 응답의 `engine` 필드가 어느 쪽이 짰는지 항상 밝힌다. 근거 투명성·재현성·응답 속도로 규칙 엔진을 메인에 놓았다.

### 정량 결과

| | |
|---|---|
| **검증기 효과** | **274개 시나리오: 1차 생성 15.0% → 루프 후 99.3%** (결정론 — `uv run python metrics.py`로 즉시 재현) |
| 테스트 | 156개 통과 · 변이 검사로 테스트 자체를 검증 |
| 재현성 | 새 폴더 clone → 설치 → 테스트 → 빌드 → API 전 경로 통과 확인. **API 키 없이 동작** |
| 인증 | JWT(액세스+리프레시) + 이메일 인증번호 가입 · 게스트 모드 항상 유지 |

**남은 미달 2건의 정체가 이 프로젝트의 백미다.** 드론정보공학과는 2026학년도 교육과정표의 전공을 전부 이수해도 43학점 — 공통 졸업요건 45학점에 2학점 모자란다(원본 PDF 재집계로 확정). 엔진의 실패가 아니라 **시스템이 찾아낸 학교 데이터의 실제 결손**이다.

## 3. AI 활용 (심사: AI 활용 역량)

### 3-1. 무엇으로 만들었나 — Claude Code 사용 구성

개발 전 과정을 **Claude Code(CLI)** 와의 페어 프로그래밍으로 진행했다. 20시간 단일 장기 세션(컨텍스트 요약으로 지속)으로 기획→설계→구현→검증→문서까지 이었다.

| 구성 | 사용한 것 | 어디에 |
|---|---|---|
| **모델** | Claude **Opus 5** (개발 세션 주력) · **Fable 5** (일부 구간) · **Sonnet 5** (제품 내 LLM 비교 모드) | 코딩·리뷰·조사 / 로드맵 LLM 에이전트 |
| **스킬** | `brainstorming` (superpowers 플러그인) | 최초 주제 선정 — 두 주제의 심사기준 배점 대비 판단 |
| | `claude-api` | LLM 에이전트(`agent.py`) 작성 — 구조화 출력·SDK 최신 패턴 |
| | `artifact-design` | 프론트 v2 확정 전, **클릭 가능한 화면 프로토타입**을 아티팩트로 제작해 팀 합의 |
| **MCP** | `playwright` (브라우저 자동화) | 3D 랜딩 시각 버그 진단, 화면 확인 |
| **내장 도구** | WebFetch / WebSearch | **할루시네이션 방지** — 졸업요건·NCS·자격증 정보를 학교/공공 원문에서 직접 확인하고 출처 URL과 함께 저장(`data/enrichment/evidence.json`) |
| **운영** | 백그라운드 프로세스(서버 기동·장기 측정), 병렬 도구 호출, `gh` CLI(이슈·PR 자동화) | 검증·리뷰 루프 |

### 3-2. 어떻게 통제했나 — 사람이 결정하고, AI가 만들고, 코드가 검증한다

- **폴더 소유권 + PR 리뷰**: AI가 만든 코드도 담당 폴더 밖이면 반드시 PR로 올려 담당자 리뷰를 받았다 (예: 서버 수정 PR에 "이견 있으면 되돌리셔도 됩니다" 명시). main 직push·force push 전면 금지.
- **위임 범위를 측정으로 정했다**: 교육과정표 추출을 LLM에 맡기려다, 35개 PDF 헤더를 전수 확인해 이름이 전부 같음을 보고 코드 파싱으로 전환했다. LLM은 폴백으로 강등(발동 0회).
- **실패를 기록했다**: AI 산출물에서 잡은 오류 6건을 `docs/AI_USAGE.md`에 위임 방식·검증 방법과 쌍으로 남겼다. 공통 교훈 — 초록불(테스트 통과)은 아무것도 증명하지 못하며, 실데이터 전수 실행과 눈으로 찍어보기가 실제로 오류를 잡았다.
- **아키텍처 결정도 비교 실험으로**: LLM 메인 → 규칙 메인 전환을 감으로 하지 않고, 두 엔진을 같은 계약으로 만들어 응답 시간(27초 vs 0.03초)·재현성·근거 투명성을 실측 비교한 뒤 팀이 결정했다.

### 3-3. 프롬프트 기록 (대표 사례)

전 과정의 프롬프트가 세션에 남아 있으며, 대표 사례를 유형별로 발췌한다:

| 유형 | 실제 프롬프트 (요지) | 결과 |
|---|---|---|
| 판단 요청 | "주제 2개와 심사 배점표를 줄 테니 **판단해달라**" | 배점 역산으로 주제 확정 |
| 사실 검증 | "학교 역량기반학사시스템에 비슷한 로드맵이 있대. **확인해줘**" | SMART CARE 분석 → "상류 공정" 포지셔닝 |
| 범위 통제 | "우선 깃허브는 건드리지 말고 참고만 해" / "PR 올리는 건 잠시 대기하자" | 접근 권한을 사람이 단계별로 부여 |
| 검증 지시 | "머지 전에 검증 한번 하자 — 문서 전부와 파일·트리 구조까지" | 교차 불일치 다수 발견·수정 |
| 반론 수용 | "LLM 대신 머신러닝을 쓰는 건 어때?" → AI의 반론(학습 데이터 부재) 청취 후 **"실데이터 기반 결정론"으로 재정의** | 심사 질의응답에 안전한 명명 |
| 원문 확인 | "(25·26년) 최신 기준으로 확인해줄래?" | 드론 43학점을 2026학년도 원본 PDF로 확정 |

### 3-4. 제품 안의 AI

로드맵 생성 LLM 에이전트(비교 모드)는 **환각 차단 2중 장치**로 설계했다: ① LLM은 카탈로그의 `course_id`만 고르고 학점·이수구분은 코드가 채운다(지어낼 여지 제거) ② 결과를 검증기가 판정하고 미달 사유로 재생성시킨다. 파이프라인의 LLM 폴백(헤더 파싱 실패 시)은 준비했으나 발동 0회였다.

## 4. 실용성 및 활용 가능성 (심사: 실용성·활용 가능성)

| 사용자 | 제공 가치 |
|---|---|
| 재학생 | 직무 역산 학기별 로드맵 + 자격증·이력서·포트폴리오 시점 + 졸업요건 실시간 검증 |
| **직무 미정 학생** | 학과 데이터 기반 직무 추천 → 추천 로드맵 (이 서비스가 가장 필요한 사용자를 내쫓지 않는다) |
| 예비 입학생 | 학과 탐색 — 34개 학과 커리큘럼·자격증·진로 열람 → 입학 전 로드맵 미리 그리기 |
| **학교 (트랙 B)** | 직무별 커버리지·자격증 결손·**졸업요건 불일치(드론 43/45)** 진단 리포트 — 교육과정 개편의 근거 자료 |

- **SMART CARE 연계**: 산출 로드맵이 기존 시스템의 입력이 되는 구조라 도입 마찰이 낮다.
- **확장성**: 파이프라인이 학과별 파서 없이 헤더 기반이라, 같은 꼴의 교과과정표를 쓰는 타 대학에 수집→추출→검증이 그대로 이식된다.
- **운영 비용**: 메인 엔진이 규칙 기반이라 서버 외 비용 0. 키 만료·네트워크 장애에도 코어가 죽지 않는다.

## 부록 B. 검증 지표 재현 값

시나리오 274개(전 학과 × 목표 직무 × 재학 시점 2종): 루프 OFF 41/274(15.0%) → ON 272/274(99.3%). 재생성 분포 1회 41 · 2회 231 · 3회 2. 잔여 미달 2건 = 드론정보공학과(전공 개설 43 < 요건 45, 원본 확정).
